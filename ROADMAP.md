# Roadmap

Known gaps and possible future improvements, not yet scheduled to any release.

## Features & correctness

- `PolishRetailBonds` currently treats every bond type identically — interest accrues as unrealized (`Profit_without_dividends`) continuously and is only recognized as realized once, at final redemption. That matches the four "compounding" types (`TOS`/`ROS`/`EDO`/`ROD`, which really do pay nothing until maturity), but not the four "flat" types (`OTS`/`ROR`/`DOR`/`COI`), which in real life pay interest out at the end of every period — cash that arguably should exit the position and register as realized at each period boundary instead of sitting modeled as still-unrealized for years. Worth a closer look at whether/how to model per-period realization for the flat types; this would change actual reported numbers for those four types, not just labels
- `Plot.performance_plot`/`benchmark_comparison_plot`/`period_return_bar_plot` each guard with `if <column> not in self.portfolio.portfolio.columns: <recompute it>`, but `self.portfolio` only ever comes into existence (always already carrying that column) inside `calculate_irr()` itself — `resample()`/`calculate_money_earned_between_dates_column()` both require it to already exist, so neither can be the first call either. Calling any of the three on a `Portfolio` that's never had `calculate_irr()` called raises `AttributeError` from the guard's own attribute access, instead of transparently computing IRR the way the guard implies — and the guard's "recompute" branch is otherwise unreachable through the public API. See `tests/test_plot_library.py`'s `test_performance_plot_on_a_never_computed_portfolio_raises_attributeerror` for a reproduction
- `Stock`'s `tickers_json` requires a `currency` field per ISIN (`{"ticker": ..., "currency": ...}`), but `yfinance` already exposes a ticker's own currency directly - confirmed via `yf.Ticker(ticker).fast_info['currency']`, which returns the right value for both a US ticker (`AAPL` → `USD`) and Polish WSE ones (`PKO.WA`/`CDR.WA`/`PKN.WA` → `PLN`). Dropping `currency` from `tickers_json` and fetching it from `yfinance` instead (once per ticker, cacheable the same way price history already is) would remove one manual, error-prone field - nothing today validates that a hand-entered `currency` actually matches the ticker, so a stale/typo'd value currently fails silently rather than loudly. `Commodity`/`Crypto` don't have this problem - every symbol already quotes in one fixed `QUOTE_CURRENCY`, no per-symbol field at all
- No validation that a source directory's CSVs actually carry the columns their state needs - `column_or_nan`-style helpers silently fill a missing/misnamed column with `NaN` instead of failing loudly. Confirmed as a real (not just theoretical) failure mode: a `buy.csv` with a mistakenly-named `penalty` column instead of `fee` silently produced `Decimal('NaN')` money values, which only surfaced many steps later as a confusing `TypeError` deep inside pandas' `cumsum()` internals rather than a clear "missing column `fee`" error at load time. A required-column check per state (`buy`/`sell`/`dividend`/...), raised immediately when a source is constructed, would fail at the actual point of the mistake
- `Stock`/`Commodity`/`Crypto` all track partial sells against a running *average* cost basis (see the README's Distribution metrics section) - a real simplification, since several jurisdictions require FIFO (or specific-lot identification) for tax reporting, not average cost. Anyone relying on this library's `Realized_profit`/`Profit_excluding_dividends` figures for actual tax filing in such a jurisdiction would get a different number than what's legally owed. Documented here as a known limitation, not a planned change - average cost is considered good enough for this library's purposes
- No portfolio-level inflation-adjusted ("real") return - the plumbing already exists at the bond level (`PolishRetailBonds` reads `interest_rate.csv`/`inflation_rate.csv` for `COI`/`ROS`/`ROD`/`EDO` bonds), but nothing exposes a real (inflation-adjusted) IRR/return for the whole `Portfolio`, which is the number that actually answers "am I ahead of inflation" rather than just "am I up in nominal terms"
- No data-quality diagnostics surfaced to the caller - e.g. how many days a ticker's price series was forward-filled for a gap, or how far a ticker's first available price date sits from its first transaction date (bridged silently today via `ffill()`/`bfill()`). A quiet data problem currently either gets silently absorbed or (see the `column_or_nan` item above) surfaces as a confusing crash much later, with nothing proactively flagging it

## Performance & reliability

- `DiskCache` caches each source's already-currency-converted result, so switching `currency_to` (e.g. viewing the same portfolio in USD vs. PLN) invalidates the cache entirely and re-fetches raw price history from `yfinance` that hasn't actually changed - only the FX conversion step needs redoing. Caching the raw (pre-conversion) fetch separately from the conversion step would let a `currency_to` change reuse the price data and only redo the FX math

## Project structure & tooling

- No `CONTRIBUTING.md` — nothing tells a contributor how to set up a dev environment, run the test suite locally, or what's expected of a PR, even though PRs are now required to merge into `main`
- No PR/issue templates (`.github/PULL_REQUEST_TEMPLATE.md`, `.github/ISSUE_TEMPLATE/`) — nothing structures bug reports/feature requests or reminds a PR author what to fill in
- No lint/type-check config (e.g. `ruff`/`black`/`mypy`) or a CI job enforcing it — only test-passing is currently checked, style and type consistency aren't
- Package modules live at the repo root instead of under a `src/<package>/` layout — the README's Project Structure section already flags this as unusual; a `src/` layout avoids the root directory accidentally shadowing the installed package during development
- No `py.typed` marker — even with type hints throughout, the package isn't PEP 561-compliant, so external type checkers won't trust its annotations
- No CLI entry point - using the library at all currently requires writing a Python script (`example_data/example.py` is the template every user has to adapt). A thin CLI (e.g. `portfolio-calc --sources sources.json --tickers tickers.json --report out.json`) would make the README's own "tracking your own investment portfolio" use case reachable without writing Python

## Extensibility

- `sources` currently only accepts a directory mapped to a string from `VALID_SOURCE_TYPES`, dispatched by a hardcoded `if`/`elif` in `Portfolio.__init__` to one of the five built-in classes (`Stock`/`PolishRetailBonds`/`Commodity`/`Crypto`/`BankAccount`) — there's no way to plug in a custom instrument (e.g. a country-specific bond/account type not covered here) without forking the library. Every existing source already follows the same implicit contract `Benchmark` documents against itself ("same contract as Portfolio.data/.portfolio"): a `.data` DataFrame with the standard `Money_invested`/`Profit`/etc. columns, `total_money_invested`, and the `distribution_by_*` dicts. Letting `sources` accept a class/callable directly (e.g. `{'my_dir': MyCustomAssetType}`), not just a string, would let a caller register their own asset type against that same contract. Would need the contract written down explicitly (it's only consistent by convention today) and the plugged-in class's shape validated at registration time, so a mismatch fails clearly instead of breaking deep inside `_absorb_source`/`merge`
- One directory per `sources` entry currently conflates two separate roles: which class parses it (the type) and how it's bucketed in `distribution_by_directory` (the sub-group). Splitting a single asset type into sub-groups (e.g. "IRA" vs "taxable" stocks) means creating a separate directory per group today, each an independent `Stock`/`Commodity`/`Crypto` instance — so a ticker held in two groups gets its price history fetched twice, independently, since `currency_cache` only shares FX rates, not price data. Keeping one directory per asset type and adding a separate grouping mapping (likely a JSON like `tickers_json`, mapping ISIN/ticker to group name) would let `Portfolio` build a `distribution_by_group` breakdown without the duplicated fetches or duplicated CSV rows. This wouldn't replace `distribution_by_directory` (still the only breakdown spanning every asset type at once) so much as add a same-type, finer-grained one alongside it - and would need every source class's CSV-loading code updated to thread the group mapping through
